# 实验480 连接词支持的零次数自环补全

2026-10-18预登记。exp476每片平均10个公式，许多公式只有一个
生成元。原提取器只把实际重复过的cycle作为变量。当前假设是连接词
经过的端口还提供其他合法自环，将其以零初始次数加入，能让同一个
公式覆盖更多二维位置。该机制只使用架构与名义路径。

固定exp476的两个源、四个目标、两个余类及四个方向，共64完整
切片、35,328个含零轴重复的值。沿用原两种tight边次序、整数
行列式求值、greedy覆盖及剩余值保存。单项候选在保留连接词访问的
每个端口加入全部非零位移、正费用的商图自环，初始次数为零。
变量仍最多两个独立生成元，其余循环按原次数吸收入连接词。

复用exp476的原模型作为对照，核对相同点、认证真值及原始路径。
每个可行新公式必须不小于真值，选中公式的连接与支持逐边重放。
比较每片公式数、残余值数、求值次数及九个int16原格式容量。
另对两臂同时使用固定紧凑格式消融，将生成元六元组放入共同字典，
每公式保存三个int16锚点和uint16字典号，根索引省去可推导的键。
计入全部索引及残余值，解码回原数值公式后再次逐点恢复。

两臂覆盖和恢复均为确定性检查。候选实际紧凑压缩容量更小时保留；
条件全160源原始小于1.5GB、压缩小于80MB时扩大切片，再形成
全源及全部端点的完整1M程序。容量投影继续采用相同每片成本及
压缩率假设。任何支持、上界或恢复检查失败立即停止。
当前局部格式通过只支持继续研究，真实CPU、acc与交付另验。

```sh
python3 validation/exp480_supported_completion.py prepare
python3 validation/exp480_supported_completion.py run
```

源码与正式入口保持，CPU发布基准为exp323。资产放在build/exp480/，
证据放在validation/results/exp480/。本机继续顺序运行，远端不新增
大文件。理论笔记为Obsidian“连接词支持的零次数循环扩展”。

## 结果

70,656条路径完成，35,328次原格式恢复与两臂各35,328次紧凑格式
恢复通过。新增公式覆盖原先167个残余点，残余比例由0.472713%降至0。
固定greedy的公式记录由640增至802，平均求值次数由10增至12.53125；
生成元组合字典由58增至114。

| 表示 | exp476基准原始B | 补全候选原始B | exp476基准压缩B | 补全候选压缩B |
| --- | ---: | ---: | ---: | ---: |
| 九个int16及引用 | 14,976 | 17,152 | 4,206 | 4,555 |
| 共享生成元紧凑格式 | 6,804 | 8,104 | 2,989 | 3,359 |

紧凑布局对原基准减少28.934855%的压缩体积，属于表示改进。
零次数补全在相同紧凑布局下增加12.378722%，固定组合容量收益
条件未过。完整恢复及新增覆盖机制保留；当前greedy以覆盖点数选
公式，编码的字节成本与覆盖点数的差异已成为下一项可检验问题。

基准紧凑格式的条件全源原始为1,306,368,000 B，压缩573,888,000 B。
候选为1,555,968,000 B和644,928,000 B。两者压缩体积均未满足
80MB条件，结束当前格式扩大。全源投影的共享及压缩率假设保持。
结构分析CPU56.161320秒，峰值RSS265,981,952 B。原始结果见
validation/results/exp480/report.json及compact-report.json。

## 准备步骤修复

首次prepare复用exp476准备器创建freeze.json后，调用只允许新建
文件的write函数追加元数据，触发FileExistsError。启动shell按换行
继续执行run，原冻结记录缺少新驱动及比较基准的身份；完整计算随后
通过。失败源码及原freeze保存在exp480-prepare-freeze-failure。

修复仅把prepare最后一次写入改为明确更新刚创建的文件。独立临时
目录的完整prepare通过，逐份核对冻结文件身份；AST对照确认计算、
覆盖选择、紧凑编码及解码函数全部保持。补全当前freeze的来源说明，
复用已完成计算，避免重复约56秒的结构分析。前置假设和原始协议
始终保留，修复记录见preparation-repair.json。

## 随机访问索引补计

紧凑文件每片存4 B数量，快速定位变长公式与残余段还需两项uint32
前缀偏移。exp481补建并检查每片8 B索引，静态压缩文件保持原身份。
按12,288,000个全源切片计算，额外运行时索引为98,304,000 B。
基准的条件运行时主体由原始1,306,368,000 B加至1,404,672,000 B，
补全候选为1,654,272,000 B。这里仍须另加完整估计器的其他结构；
1.5GB门保留其余进程空间。四个紧凑资产的偏移已逐片核对，
证据见exp481/runtime-index-accounting.json。
