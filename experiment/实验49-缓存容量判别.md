# 实验49 缓存容量与重复/独特请求判别（预注册）

日期：2026-09-24。目的：补齐不同 query-cache 容量及重复/独特负载的成本证据。实验只使用冻结正式二进制，
不改 `./estimate`、`build/submission/` 或源码，不读 golden，不产生生产候选。

## 假设与停止条件

- H1：重复请求在缓存能容纳完整 distinct key 集合时，CPU 明显低于 cache=0；容量不足时命中率和 CPU 随容量变化。
- H2：独特请求的 CPU 与容量基本无关，命中率为零。
- 只做筛选性判别。若非零容量没有可重复的命中或 CPU 改善，保持 64 MiB；不据此改默认容量。

## 冻结身份

- 二进制：`./estimate`，实验29正式 SHA 在运行 JSON 中记录。
- 架构：`doc/eda比赛文件/arch`，五个 JSON 的 SHA 在运行 JSON 中记录。
- 输入：同一架构和请求格式生成 2,000,000 行 repeated（公开 1M 请求重复两次）与 2,000,000 行 unique（实验31 unique 输入前 2M 行）。输入生成后记录完整 SHA、字节数和行数。
- 容量：`0, 4, 16, 64` MiB。`0` 为无缓存，16 MiB 预计覆盖约 1M key，64 MiB 为正式设置；不按结果增删容量。

## 计时协议

输入重建命令：

```sh
head -n 2000001 build/exp29/requests-100m.csv > build/exp49/requests-2m-repeated.csv
head -n 2000001 build/exp31/unique-4m.csv > build/exp49/requests-2m-unique.csv
```

每个输入分别运行四个容量各两次，共 16 次，串行、`taskset -c 3`、同一工作目录。每个输入的顺序固定为
`0,16,4,64,64,4,16,0`（第一轮和第二轮交错），不做预热；每次用 `scripts/run_scale.py` 记录 user/sys CPU、wall、峰值 RSS、线程、缓存命中、建表秒数、退出码和输出 SHA。输出只写实验目录，运行完成后按 SHA/重建命令记录并删除可重建输出。

门槛：每次退出码为 0、线程为 1、RSS×1024 ≤ 2,000,000,000、wall ≤ 3,600 秒、输出行数和 From/To 顺序与输入一致。同一输入的同一容量两次输出 SHA 必须一致。结果只作描述统计，不作正式综合分验收。

## 预注册分析

按容量报告命中率、CPU 中位数/范围、建表秒数、RSS 和输出 SHA；比较 repeated 与 unique 的容量曲线。若容量 16/64 MiB 的 repeated 命中率接近 100% 且 CPU 相对 0 明显下降，而 unique 均为 0 命中，则支持保留有限缓存并将收益限定为重复负载。任何结论只适用于本输入分布，不能外推赛方隐藏输入。

## 结果

输入哈希：repeated `598483a2c51e3c1c06768d00d374bfdd99ec6f7f907e8f810c78967fbe48a5fb`，
unique `6ec7c94e453d56a4454b078f52abd75f270992d55e99752dca35e0b010903b20`；两者均为
2,000,000 行。正式二进制 SHA 为 `db2cca1e…`。一次误带 `-quiet` 的 repeated/c0 运行
（`repeated-c0-r1.json`）没有命中计数，保留为无效记录；统计使用 `r1b` 和 `r2`。

| 输入 | cache MiB | CPU 中位数（s） | cache_hits | RSS（KiB） | 输出验证 |
| --- | ---: | ---: | ---: | ---: | --- |
| repeated | 0 | 71.19 | 0 | 838,100–838,212 | 2/2 通过 |
| repeated | 4 | 67.03 | 196,608 | 838,148–838,208 | 2/2 通过 |
| repeated | 16 | 55.87 | 786,432 | 838,056–838,208 | 2/2 通过 |
| repeated | 64 | 51.15 | 1,000,000 | 903,652–903,744 | 2/2 通过 |
| unique | 0 | 68.22 | 0 | 838,100–838,208 | 2/2 通过 |
| unique | 4 | 73.81 | 0 | 838,056–838,112 | 2/2 通过 |
| unique | 16 | 72.12 | 0 | 838,048–838,128 | 2/2 通过 |
| unique | 64 | 73.08 | 0 | 903,740–903,744 | 2/2 通过 |

重复输入的 64 MiB 容量正好容纳首个 1M distinct key，第二块全部命中；16 MiB 和 4 MiB
分别只能保留 786,432 和 196,608 个 key。unique 输入在所有容量下均无命中，CPU 差异在本机计时波动内。
所有有效运行均为单线程、退出码 0、RSS×1024 小于 2,000,000,000，输出分别只有一个 repeated
SHA `65c7e4fdf1a715170f9d5bd857b91d8fc994092e467faf212476e7017d06cf8b` 和一个 unique SHA
`812b651eef429c91d0463abe6b74e27caaf9e5a330441377f5eb1d757fd9b64f`。

结论：缓存收益依赖重复 key；64 MiB 在本重复负载上比无缓存中位 CPU 少约 20 s，unique 负载没有收益。
保留正式 64 MiB，不增加容量或改缓存实现。输出 CSV 已在哈希核对后删除，输入、原始 JSON、stderr、time 和验证文件放在
`validation/results/exp49-cache/`，汇总为 `validation/results/exp49-cache-summary.json`。
