# 实验379 共享5位父链的在线等价与Xeon筛选

2026-10-17，生成在线表和查看新计时前登记。承接exp378共享5位容量结果，
只改变exp354的父表表示。当前40树共877,212,320槽，每目标Z最多22个实际值。
exp336旧Xeon U-output采样中UpperTree::evaluate占4.10%，父表只占其中部分。
因此本轮预期是局部访存和内存改善，完整CPU收益仍受搜索等其他费用限制。

固定候选使用全部40树共享的每Z升序字典，补齐32项，未使用项为255。
每树按原扁平槽顺序连续保存5位编号，末尾额外1个零字节供双字节读取。
全树同宽省略逐平面描述符，保留原树边界与元数据。原frame逐树解压核对
原raw SHA，生成离线5位数据，再以原有zstd的19级压缩。生成过程完整逆变换
核对；字典、元数据和新blob一起冻结。生产根入口和交付包保持exp354。

改动范围仅私有build/exp379/src/upper_tree.h、生成的
embedded_upper_tree_data.h、新父表object以及必要的实验工具和检查。
调用者仍为UpperTree::init、evaluate和ResidueEstimator::applyUpperTree。
模型、映射、累计费用、搜索计数、合法性检查、校准、缓存和I/O保持原调用。
普通生产构建参数沿用exp353，使用通用-O2，不启用机器专用指令。

主假设是5位表减少父链随机访问的内存费用，能够抵偿位提取和字典读取，
并保留每个parent值、候选路径、模型特征与输出。竞争解释是解码增加的
指令依赖使CPU上升；容量收益单独记录。容量预登记按连续流重新计数，
与exp378逐平面取整和描述符表示的差别分别说明。

检查顺序如下。

1. Python编码的全部槽往返及raw SHA；C++直接调用实际parent方法重放全部槽，
   核对40树根、255、尾部、四边界；同一检查再运行ASan/UBSan。
2. 对build/exp257/requests.txt的12,150条已查看开发请求，单独调用UpperTree，
   比较exp354与候选的所有Result字段、浮点位型、26特征、9个pathSummary及
   parent/resolver/recovery/replay计数。逐槽相同与原恢复代码共同支持路径等价。
3. 复用exp353四个exact开发集及边界、现有特殊输入，候选完整输出SHA相同；
   不新增exact。源代码身份相同的搜索路径验证沿用exp353已有通过证据。
4. 本机20k和Xeon完整公开非重复1M输出契约及资源检查。公开golden评分
   在候选完整输出SHA等于exp323/354时复用99.01069721418632%，配对变化0行；
   分组误差保持。精度余量仍只有约0.0107百分点，继续单列为局限。

Xeon核3、单线程、串行，先各臂20k预热，再完整1M三轮交错：
exp323/exp354/5bit，5bit/exp354/exp323，exp354/exp323/5bit。
使用scripts/run_scale.py，记录user+sys、wall、RSS、线程、初始化和完整输出
身份。原发布默认exp323（cache64）固定为CPU基准；exp354和候选cache0。
各臂必须cache_hits=0。缓存差异作为已有工程收益，5位增量以exp354对照。
启动前保存进程负载；已有重负载结束后再启动。

主指标是完整1M CPU差与配对95%t区间（df=2，包含计时舍入范围），同时报告
初始化、稳态近似分解和峰值RSS。最小实际收益预先定为完整1M节省0.2秒，
且候选相对exp354与exp323的差区间上界均小于0，才进入本轮10M。
CPU差区间跨零时保留待定；明确变慢则结束本轮固定布局的放大测试。
AMD结果只作成本参考。资源要求单线程、峰值RSS<=2,000,000,000字节、
每次<=3600秒，完整输出3字段、整数delay、端点顺序、精确EOF、SHA和多次一致。
任何等价检查失败先停止新计时并保留失败证据。

本轮10M若获得资格，另登记计时顺序和必要成本。100M与1B均待后续扩大，
本轮不把容量或小规模外推记作阶段成绩。开工/dev/sdd可用约387GiB；
新生成文件可由本脚本重建，清理沿项目逐项规则执行。
