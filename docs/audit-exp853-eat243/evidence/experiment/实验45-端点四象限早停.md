## 假设与机制

`estimateEndpoint` 对 Source、Target、Both 的每个 endpoint 叶调用 `estimateBase`，叶内四象限取 max 循环每次加载 4 个 `tableSlot`（mult2 下表容量 813,957,120 bytes）。调用者此时已有非负 incumbent `best`：叶只有在 `prefix + middle + suffix < best` 时才可能改进。于是可在四象限扫描中维护单调不减的 partial max：一旦它能证明该叶的最终值 >= cutoff（cutoff = best − prefix − suffix），剩余象限就不必再查。

判据用保守整数形式：进入循环前算一次 `cutoffScaled = (int64_t(cutoff) − line) * scale_`，partial max 满足 `best >= cutoffScaled` 即判该叶不能改善。充分性：`llround` 单调不减且 `llround(整数 K) = K`（K = cutoff − line），只要 `scale_ > 0` 且 int64 乘积在范围内，`best >= K*scale_` 就蕴含 `llround(best/scale_) >= K`，再经 `max(0, ·)` 仍 >= cutoff；负 K 同样成立。每象限不做 `llround`。形参是 `int cutoff = -1`，-1 表示不剪（root 与尚无 incumbent 的调用者）；三个 endpoint 调用点都先按 `prefix >= best` 提前 break，所以真实 cutoff 严格为正，没有 `cutoff <= 0` 的预剪分支。

几何事实用实验36 的 span 自检与初始化日志：mult2 模数是 20×24，`scale_ = lcm(20,24) = 120`；架构最大净位移是 10 和 12；芯片 120×550 是坐标边界，与模数无关，不用芯片宽高猜 scale。

## 保留语义

- root `estimateBase` 完整计算，不传 cutoff；`base.value`、`base.fallback`、模型特征、`shortUpper`、bounds 路径都不变。
- 只在 Source/Target/Both 的 endpoint 叶传 cutoff，且只有 `best >= 0`（已有真实 incumbent）才传。
- same-pin、无效端点、`unreachable`、`kInfTable` 跳过、all-INF 直线 fallback、I* 目标位移折叠、四象限 max 顺序、`llround`、mandatory Line、`max(0,...)` 全部保留；剪枝只在已看到至少一个有限象限后生效，all-INF 叶仍走 fallback。
- 返回契约显式：`BaseAnswer` 增加 `pruned` 标志，剪枝叶的 `value` 只作“已达 cutoff”标记，三个调用点在读 value 之前先跳过 `pruned`，不会被当成完整 base 答案用于其它路径。
- 最小改动，不加生产 CLI 开关、包装器或新依赖。

## 我独立指出的风险路径

1. all-INF 叶被 partial 值剪掉：只有 `haveQuadrant` 后判据才成立，否则 fallback 会丢。
2. Line 用错端点：cutoff 必须用该叶自己的 mandatory Line（与最终值同源），不能借 root 的。
3. I* 目标：partial max 必须用折叠后的 `lookupDx/lookupDy/lookupResidue`，用原始 dx/dy 会错。
4. 半整数与负数边界：保守判据对任意符号都充分；若改精确判据，要分别证明 x>=0 与 x<0 的 llround 规则。
5. incumbent 语义：`best` 初始 −1，只有 `mergeMin` 真正写入后才可传 cutoff；用 prefix 单项当 incumbent 会错。
6. Both 前缀和：cutoff 必须与内层 break 用同一个 `exit.cost + entrance.cost`。
7. `mergeMin` 严格性：剪枝假设“严格更小才改进”，当前 `mergeMin` 用 `<`；若改成 `<=` 必须同步改判据。
8. root 误用剪枝叶值：`pruned` 必须显式短路，不能靠 value 碰巧不出错。
9. 溢出：`(cutoff−line)*scale_` 用 int64；cutoff/line 为 int 量级，scale=120。

## 计数诊断

与原生计时分开：用最少的编译期计数（`#ifdef EXP45_COUNT` 下的文件级计数器：实际 table loads、早停次数、estimateBase 调用数、剪枝时省掉的槽数）在候选构建上测实际开销。同路径无剪基线用 `actual_loads + saved_loads`，因为 same-pin 与无效端点会在读表前返回，`4 × 调用数` 不是精确基线。公开 1M 前 20,000 条（残差 off 的计数构建）实测 actual 3,090,836、saved 1,947,308、early 942,694、base_calls 1,259,536，`actual + saved = 5,038,144`，与实验35 callgrind 基线（公开 1M 前 20,000 条 xgb 的 5,038,144 次四象限加载）一致；计数构建标注为 residual=off，性能协议仍用 xgb。当前四象限槽已相邻（每叶 16 字节），减少 load 不自动等于减少 cache line 访问，取舍以原生 CPU 为准；原生计时二进制不带计数开销。

## 冻结计时协议

两份已有 1M 独特输入：`delay_estimate_request.csv` 与 `build/exp35/new-arch-1m.csv`。`tests/exp31_phase2_query_cost.cpp` 编译两份 harness（before = 当前源码；candidate = 只加早停），参数 `--mode off --residual xgb --repeat 1`（harness 固定 cache=0、mult2、SourceShort 150），`taskset -c 3`，同编译参数 `g++ -std=c++17 -O2 -Wall -Wextra -Wno-unused-parameter -I src`，单进程单轮，不并发。

每份输入按 B,C,C,B,B,C,C,B 八轮（四对相邻配对）；每轮记录 build CPU/wall、query CPU/wall、RSS、checksum、表字节，全部保留，不丢慢轮、不看中间结果改顺序。每份输入的四个 candidate−before 配对差用 t(df=3)=3.182446 报均值和 95% 区间；两份输入的区间上界都 < 0 才允许进入下一规模，否则 inconclusive/off。每轮硬超时 1800 s，留 PID/状态；超时或失败保留并报告，不自动重跑。这只是本机 query 筛选，不声称 1B/SOTA 收益。
