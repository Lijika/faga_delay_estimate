# 实验784 完整曲面码号局部性门槛

2026-10-28预登记，正式版exp780。exp781对未知非重复100M
精度+0.074890pp而CPU+1.677024秒；exp783两对完整运行
显示LLC misses平均多4661万/100M，指令数稍降。
exp782全域逐列固定uint8无损范围门失败。

主假设是8192个主体码出现明显访问偏斜。若常用码构成
较小热集，启动时对码本和目录码号做一个无损排列，
有望改善局部性且不改变精度和静态ELF资产。第一阶段只读
exp781已恢复的全208源目录`build/exp781-full/records.u32`，
四方向分别统计全部pair×context记录的码号频率，
登记前256、512、1024、2048、4096码覆盖率，并与
百万已观察生产开发缓存的实际pair×context码频作对照。
后者只作人口压力测试，不能代表官方未知1B。

若每方向前2048覆盖≥75%且前1024覆盖≥60%，再研究只在
启动时做码号排列：目录和码本必须同步置换，保持编码中心、
二级码本及全部输出逐点不变。否则固定只重排码号的配置停止，
转向同时减少运行字节与地址依赖的不同表示。
这个门是访问结构机会筛选，不是性能证明。审计CPU预算
60秒，临时RSS低于1GB，不运行新的估计程序。

实际候选须分别核对恢复字节、全部代码本映射、200万开发
逐行整数输出身份、静态ELF<100MB、RSS<2GB和启动CPU；
随后复用exp781已观察100M做六对完整配对，正式阶段
基线及+0.02综合分门与exp781一致。正向结果再进行独立
非重复1B验证。频率统计本身不能作为1B精度/CPU成绩。

## 实测与边界

`validation/results/exp784/frequency.json`的独立脚本审计先用
百万开发缓存核对全208源目录码，再分别统计四方向。
前1024覆盖29.20%至30.49%，前2048覆盖48.47%至50.23%，
前4096覆盖75.68%至77.14%。百万开发人口的前2048覆盖
48.63%至49.89%，与全目录没有显著的高频集中。
四方向全部未达到前1024的60%与前2048的75%门，
固定“只重排码号”的实验停止。统计CPU0.663118秒，
峰值RSS332976128B；没有运行新的完整估计程序。

这些覆盖率只说明本次码号置换的局部性机会不足；代码本
按访问频率重新训练、拆分热子域或降低依赖层数尚未测试。
目标机6242R为双路各约35.75MiB的L3，实测r9为单路
6226R、22MiB。exp783的LLC增量只在r9成立，
既不能把两个socket的L3合并，也不能把同一增量直接投射
到6242R。后续优先比较CPU能力分派与整体表示，现有
`-march=x86-64 -mtune=generic`作为安全基准。
