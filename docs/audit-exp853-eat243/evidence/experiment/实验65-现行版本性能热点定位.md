# 实验65：现行版本性能热点定位

日期：2026-09-26。开工时 `/dev/sdd` 可用491G。

## 测量协议

- 当前正式源码二进制 `./estimate` SHA-256 `74c86335b4adbeff3f4012199b38509205e976d4684dae102dc05446bbf7ad11`；冻结1M unique输入 `build/exp57/timing-1m-unique.csv` SHA-256 `2cf587f1b27ccc5699040e64ea3efc6eb68c100cfd72a36cad383383a018d7bd`。正式输出完整SHA应为 `c17380dddfeba86addf764bad79a887eb25bab8544d4f64f69d8cb3097fe7e19`。
- 基准沿用实验63未改代码、输入和机器的3轮动态候选记录，CPU `42.51/41.66/41.45 s`，单线程、最大RSS `925,757,440 B`。本轮先运行一次 `perf record` 的完整1M unique路径，读用户态调用栈和热点；必要时追加一次 `perf stat` 测 cycles/instructions/cache misses。profiling运行不作正式CPU点估计。
- 主假设尚未选定：固定建表、distinct请求推理/端点处理、输入输出三个阶段可能贡献主要CPU。按实际样本和既有实验测量给热点分类后，才列单变量优化候选与预计回报。
- 复杂度口径沿用 `[[综合分CPU换算与distinct摊销]]`：一次建表成本，distinct计算随 `K` 增长，输出和缓存探测至少随 `N` 增长。实验61给出每个模型cache miss处理64棵深度8树；任何I/O优化仍要保持每行端点、整数delay和精确EOF。本文只把这些作为成本分类，不提出新图算法定理。
- 若 `perf` 无法可靠采样，改用现有组件探针/Callgrind，并记录失败原因。选候选后仅改一个变量，数值等价、完整SHA、单线程和RSS门槛先验证，再做预热后3对交错CPU比较；明确repeated与unique适用范围。

## 结果

`perf record -g -e cpu-clock:u` 的完整1M运行有4,265个用户态样本，丢样0，输出SHA与冻结值一致。`perf report --no-children` 显示建表二叉堆 `__adjust_heap` 32.80%、`__push_heap` 4.48%，`runResidueDijkstra` 本体14.72%；请求 `quadrantDiagnostics` 28.51%、`fillTargets` 8.28%。一次 `perf stat` 测得 cycles 166,616,850,969、instructions 176,655,734,506、cache misses 1,211,575,448、IPC 1.06，输出仍为冻结SHA。这是热点定位，不当作配对CPU比较。

单变量候选在 `runResidueDijkstra` 复用 `RadixFrontier`。重加权边已由 `buildPotentials` 检查非负；每轮以最小种子距离平移 `uint32_t` 键，故保留可能为负的原种子距离。证明及边界见 `[[residue多源Dijkstra的radix键条件]]`。私有构建 `build/exp65/estimate-radix` SHA `391f765c53edb12c8dcf079d9ca85435fc3116afb3ef86f6186efcec58ebef99`，一次完整1M输出SHA与基线相同。`build/exp65/verify_estimator --quick --residue-mult 2` 全部通过，两份冷表的3,469条查询差异0。

看过一次候选完整输出后，在正式配对前固定门槛：完整输出相同、单线程、RSS≤2,000,000,000 B、wall≤3,600 s，CPU差95%区间上界<0，点综合收益≥0.01。`build/venv-ml/bin/python validation/exp65_timing.py` 在同一1M unique输入预热后交错3对；候选减基线CPU依次为 `-7.35/-6.31/-6.05 s`，均值 `-6.57 s`，95%区间 `[-8.279,-4.861] s`。精度逐行相同，因此综合点收益 `+0.05475`，保守下界 `+0.04051`。所有8次运行输出SHA均为 `c17380dddfeba86addf764bad79a887eb25bab8544d4f64f69d8cb3097fe7e19`，最大RSS `925,765,632 B`，单线程。原始证据为 `validation/results/exp65-timing-1m-unique.json`。

该优化只改变一次建表成本；unique与repeated的请求推理和输出路径相同。3对结果证明已测1M unique负载的CPU收益；1B与隐藏集待平台运行，其他输入规模的收益只可按一次建表节省约6.57秒作条件外推。公开1M未用于模型或阈值选型。配对时基线命令是当时的 `./estimate`；正式源码构建后，复现脚本改指向二进制SHA相同的冻结副本 `build/exp63/estimate-candidate`。

正式源码构建的 `./estimate` SHA与私有候选相同。提交 `a4594e3` 后，`ALGO_VERSION=exp65-radix-table VERSION_LABEL=exp65-radix-table-a4594e3-dirty sh scripts/build_submission.sh --verify` 创建不可变包；静态 bin SHA `7a925a0f5cde216f025c75bfb9570df669db6ca21faf040ec9df3a88a157a23e`，zip SHA `3dd67d2a0bddff55c18a2aea5c9d9f8a48d335ea2ad430bf11b6402f4f8852d5`。clean-room、公开1M SHA `99dc587b98718fd63213bf6f44a497b5970c199fc444c01dbeb30401c004d41c`、3,107条holdout逐字节核对通过。

正式构建的 `build/verify_estimator --quick --residue-mult 1` 也通过，两份冷表的3,469条查询差异0；默认mult2已由上面的私有验证和完整1M检查覆盖。

`build/venv-ml/bin/python validation/exp65_package_1m.py` 对包内二进制完整运行3次1M unique，CPU `36.53/35.27/35.32 s`，最大wall `36.44 s`、RSS `923,791,360 B`、线程数1。每次都核对表头、1,000,000行原端点顺序、恰好3字段、整数delay、精确EOF及完整SHA，三次结果均为 `c17380dddfeba86addf764bad79a887eb25bab8544d4f64f69d8cb3097fe7e19`；原始证据 `validation/results/exp65-package-1m-unique.json`。`subm/versions/`、`subm/latest/`、`subm/submission.zip` 三处zip SHA相同。

收尾时 `/dev/sdd` 可用490G，本轮未删文件，释放量0；相对开工时491G的显示值少约1G，主要是本轮测量输出与包。没有满足本轮清理规则且需要删除的大文件。平台1B和隐藏集成绩仍待平台回执。
