# 实验815 实际双码组合的精确启动展开预算

2026-10-29，预登记。exp813和814的单次完整形状读取在固定32位
目录下均未过名义质量门。本轮检验另一种信息保持方式，将冻结A+B
在实际使用的码对上预先相加，运行时按紧凑编号读取一个和。
当前exp811的1B验证独立进行，正式入口仍为exp806。

## Altitude

固定原码本与全域目录，保留所有预测信息。静态继续保存两个小码本，
启动时从全部28,753,920条目录建立每方向的实际码对集合，再展开其和。
完整笛卡尔积最多4×2048×256×552×2=2,315,255,808B，
已经超过2GB；实际使用集合的大小决定是否值得实现。
该集合来自认证全域架构资产，与未知请求的重复命中无关。

## 固定审核与停止条件

1. 输入使用exp810完整目录及原A2048/B256码本，完整SHA核对。
2. 四方向独立统计实际码对数，用直方图和排序去重交叉核对；
   完整码号压缩再展开保持每条记录，偏置字段保持。
3. 对全部实际码对的552个格点用int32相加，验证结果可存int16。
4. 保守内存账为历史RSS269,049,856B加全部和表、8,388,608B映射表、
   67,108,864B额外预留。总额≤1,900,000,000B才构建完整程序，
   该账只作筛选；真实峰值、初始化CPU与完整CPU另验。
5. 离线审核CPU≤300秒、wall≤300秒、地址空间≤2GiB。
   未过门停止全实际集合完整552格展开；保留共现结构数据。
6. 通过后保持四阶段批8与原数值顺序，先组件等价，再100M六对；
   预登记100M平均节省至少0.25秒且95%下界为正，随后及时1B。

## Tactical与Depth

静态压缩格式与运行时查询表示可分开选择。合并A+B可减少读取次数，
同时放大热数据；查询CPU可能因缓存和TLB成本上升。
本轮先测量实际共现数与完整资源，完整计时负责判断这一交换。
全部格点范围和重映射应经过验证，原浮点后续计算保持。

证据保存validation/results/exp815/；脚本为
validation/exp815_live_code_pairs.py。本地/dev/sdd开工可用266GiB。

## 结果

四方向实际码对数分别为266,255、274,638、287,742、282,532，
共1,111,167个；完整和表1,226,728,368B，保守总账1,571,275,696B，
通过1.9GB筛选门。全部实际和的范围为[−380,602]，int16可完整保存。
28,753,920条目录逐条重映射恢复相等，直方图与排序去重结果一致。
审核CPU7.306897262秒、wall6.732744573秒、RSS683,057,152B。

初次启动调用了辅助模块中不存在的read函数，在读取数据和创建结果目录前
退出；改为标准库JSON读取后完成审核。未改数据、资源门或算法。
以上是离线全域信息与预算审核，完整启动峰值和CPU仍待验证。
