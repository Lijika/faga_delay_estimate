# 实验15 选择性 target endpoint 修正（source-short）

日期 2026-09-17，基线提交 011efa5。目标：不改现有 source/both 算法，只加一个查询调度策略——
Manhattan 距离 ≤ 阈值的请求走 `both`，其余走 `source`——并测量它是否在公开集与独立 exact
留出集上稳定优于 `source`，且成本可接受。

**结论**：策略在公开 1M 与 10M 重复负载、以及两个独立 exact 留出集上都优于 `source`（留出集
达到 `both` 水平、0 行变差），成本介于 source 与 both 之间，故默认提升为
`-endpoint-mode source-short -endpoint-short-distance 150`；`off/source/target/both` 保持
逐字节兼容。

## 1. 实现（3 个文件，无新算法）

- `residue_estimator.h`：`EndpointMode::SourceShort`；`Options::endpointShortDistance`（默认 150）；
  `Stats::shortBoth/shortSource` 计数器；`estimateEndpoint(..., EndpointMode mode)` 改为接收
  生效模式。
- `residue_estimator.cpp`：`estimate` 在 base/off 判定之后、端点枚举之前做一次纯几何分派：
  `manhattan = |tx-sx| + |ty-sy|`，`<= endpointShortDistance_` 则用 `Both`，否则 `Source`，
  并计数。分派发生在任何结果被写入缓存之前（`estimateText` 只缓存最终答案），中间段仍走
  `estimateBase`，无递归；same-pin、invalid、I/logic 端点的语义与 `Source`/`Both` 完全一致。
- `main.cpp`：`-endpoint-mode source-short`、`-endpoint-short-distance N`、usage 与结束计数器。

策略不引入任何新公式：被选中的请求执行的就是 `both` 代码路径，未选中的执行 `source` 代码路径。

## 6. 默认决策

提升为默认 `source-short`（阈值 150）的依据：

1. 公开 1M accuracy +0.30（93.2407 → 93.5419，确定性、非噪声）；
2. 两个独立 exact 留出集达到 both 水平且 0 行变差；
3. 成本门槛通过：CPU 比 source 多 13.4s/1M、15.2s/10M（约 0.7% 的 1800s 预算），RSS 不变；
4. 1M 与 10M 两个尺度上综合分都最高，且从未低于两个基线。

兼容性：`-endpoint-mode off` → `3044018c…`、`source` → `a9271af4…`、`both` → `c2238392…`
全部与历史逐字节一致；阈值可用 `-endpoint-short-distance N` 消融。

## 8. 未验证边界

1. 官方 1B 规模未测：若该规模下 time_score 对多数配置归零，accuracy 更高的 `both`（93.6702）
   会反超 ss150（93.5419）约 0.10 分；若时间分有效，则 ss150 领先 `both`（10M 口径 +0.09）。
   默认选择在两种情形下都不极端（保留 87% 的 both 精度增益，成本约 60%）。
2. 阈值与收益关系只在公开 1M 分布上扫描；其它请求分布下最优点可能不同（留出集上 32/100 即饱和）。
3. dispatch 只看 Manhattan 距离，未用端口类别或区域；未测与 bias/PDB floor 的组合。
4. `both` 路径的中间段仍是 residue 估计（非 exact），只是端点处理更完整。
